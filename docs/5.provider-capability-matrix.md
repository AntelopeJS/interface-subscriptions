description: Which payment providers fire renewals themselves, which implementation each one needs, and where native and fallback behaviour differ.

Whether a provider fires renewals itself decides which implementation a
deployment needs. The matrix was checked against the documentation of each
provider on 2026-09-18. Stripe and PayPal were not checked again then, because
both have first-class subscription objects that bill on their own schedule.

| Provider     | Who fires renewals | Implementation                                                |
| ------------ | ------------------ | ------------------------------------------------------------- |
| Stripe       | Provider           | Native, in `@antelopejs/stripe`                               |
| PayPal       | Provider           | Native                                                        |
| Mollie       | Provider           | Native                                                        |
| Adyen        | Merchant           | `@antelopejs/payment-subscriptions`                           |
| Checkout.com | Merchant           | `@antelopejs/payment-subscriptions`                           |
| Mangopay     | Merchant           | `@antelopejs/payment-subscriptions`, with a provider schedule |

- **Mollie**: _"When using this API, we automatically create recurring payments
  for you at the interval you specified."_
- **Adyen**: subscriptions are _"recurring transactions you initiate at regular
  intervals"_, against a stored token and `shopperReference`.
- **Checkout.com**: no subscription or billing-plan resource at all. A
  recurring charge is a stored instrument plus `payment_type: Recurring` and
  `merchant_initiated: true` on an ordinary payment.
- **Mangopay**: the Recurring PayIn Registration stores frequency, dates, and
  amounts, and handles the authentication chain between charges. But _"the
  platform can initiate payments"_, so Mangopay does not fire them. The fallback
  owns the clock. It can record the schedule with Mangopay through its provider
  schedule interface (`ProviderSchedule`).

Two implementations exist: the generic fallback, and Stripe natively in
`@antelopejs/stripe`. `@antelopejs/stripe` passes the conformance suite against
Stripe in test mode. Its tests on Stripe test clocks also cover what the portable
suite cannot pin: renewal, trial end, `past_due`, and cancellation at period end.
PayPal and Mollie are plans.

Implementations keep times at the precision of each provider, and the contract
promises only the second. Stripe stores seconds. The subscription `startDate` of
Mollie is a calendar date, so on Mollie a trial end or a billing anchor lands on
a day, not an instant. A native Mollie implementation has to document that, or
charge the first period itself. This is not verified against Mollie.

## Where native and fallback differ, and the contract allows it

| Behaviour                     | Native                                                                                 | Fallback                                                                                                      |
| ----------------------------- | -------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------- |
| What happens after `past_due` | The provider's configured retry schedule                                               | By default three retries, one, three, and seven days apart, then the subscription ends                        |
| When a renewal is charged     | The provider's scheduler, near the time                                                | At the time with Redis wired; within one poll otherwise                                                       |
| `vendorData`                  | What the provider said                                                                 | The fallback's own renewal state: `reconciliationRequired`, `attemptStartedAt`, `attemptReplayUntil`, `phase` |
| Events                        | From the provider's webhooks                                                           | From its own clock, recorded with each change                                                                 |
| An event's subscription       | Stripe invoice events read it back at delivery, so a redelivery can show a later state | As it was when the event happened                                                                             |

## Out of scope, and why

| Feature                        | Why it is out                                                                        |
| ------------------------------ | ------------------------------------------------------------------------------------ |
| Proration                      | Arithmetic every provider does differently, and the fallback would have to invent it |
| Dunning schedules              | Native providers configure retries in their dashboard; only the status is portable   |
| Tax                            | A tax engine is a separate product                                                   |
| Coupons and discounts          | Provider objects with provider semantics                                             |
| Metered and usage billing      | Needs usage reporting the fallback has no source for                                 |
| Several items per subscription | Needs proration to change any one of them                                            |
| Write-through `vendorData`     | It compiles everywhere but works on one provider, which hides the coupling           |
