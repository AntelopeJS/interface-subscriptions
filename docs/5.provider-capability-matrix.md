# Provider capability matrix

Which providers fire renewals themselves decides which implementation a
deployment needs. Checked against each provider's documentation on 2026-09-18;
Stripe and PayPal were not re-checked then, both having first-class subscription
objects that bill on their own schedule.

| Provider     | Who fires renewals | Implementation                                                |
| ------------ | ------------------ | ------------------------------------------------------------- |
| Stripe       | Provider           | Native, in `@antelopejs/stripe`                               |
| PayPal       | Provider           | Native                                                        |
| Mollie       | Provider           | Native                                                        |
| Adyen        | Merchant           | `@antelopejs/payment-subscriptions`                           |
| Checkout.com | Merchant           | `@antelopejs/payment-subscriptions`                           |
| Mangopay     | Merchant           | `@antelopejs/payment-subscriptions`, with a provider schedule |

- **Mollie**: _"When using this API, we automatically create recurring payments
  for you at the interval you specified."_
- **Adyen**: subscriptions are _"recurring transactions you initiate at regular
  intervals"_, against a stored token and `shopperReference`.
- **Checkout.com**: no subscription or billing-plan resource at all. Recurring
  is a stored instrument plus `payment_type: Recurring` and
  `merchant_initiated: true` on an ordinary payment.
- **Mangopay**: the Recurring PayIn Registration stores frequency, dates and
  amounts, and handles the authentication chain between charges, but _"the
  platform can initiate payments"_ — Mangopay does not fire them. The fallback
  owns the clock and can record the schedule with Mangopay through its provider
  schedule seam.

Implemented: the generic fallback, and Stripe natively in `@antelopejs/stripe`,
which passes the conformance suite against live Stripe and is further tested on
Stripe test clocks — renewal, trial end, `past_due` and cancellation at period
end — which the portable suite cannot pin. PayPal and Mollie are plans.

Times are kept at each provider's precision, which the contract only promises
to the second: Stripe stores seconds. Mollie's subscription `startDate` is a
calendar date, so on Mollie a trial end or billing anchor lands on a day rather
than an instant — a native Mollie implementation has to say so, or charge the
first period itself. Unverified against Mollie.

## Where native and fallback differ, and the contract allows it

| Behaviour                     | Native                                                                               | Fallback                                                  |
| ----------------------------- | ------------------------------------------------------------------------------------ | --------------------------------------------------------- |
| What happens after `past_due` | The provider's configured retry schedule                                             | Three retries, one, three and seven days apart, then ends |
| When a renewal is charged     | The provider's scheduler, near the time                                              | At the time with Redis wired; within one poll otherwise   |
| `vendorData`                  | What the provider said                                                               | Absent                                                    |
| Events                        | From the provider's webhooks                                                         | From its own clock, recorded with each change             |
| An event's subscription       | Stripe invoice events: read back at delivery, so a redelivery may show a later state | As it was when the event happened                         |

## Out of scope, and why

| Feature                        | Why it is out                                                                        |
| ------------------------------ | ------------------------------------------------------------------------------------ |
| Proration                      | Arithmetic every provider does differently, and the fallback would have to invent it |
| Dunning schedules              | Native providers configure retries in their dashboard; only the status is portable   |
| Tax                            | A tax engine is a product of its own                                                 |
| Coupons and discounts          | Provider objects with provider semantics                                             |
| Metered and usage billing      | Needs usage reporting the fallback has no source for                                 |
| Several items per subscription | Needs proration to change any one of them                                            |
| Write-through `vendorData`     | Compiles everywhere, works on one provider: invisible coupling                       |
