A subscription changes while nobody is calling, so a backend learns of renewals,
failures, and endings from events.

## The event set

| Type                             | When                                                                         |
| -------------------------------- | ---------------------------------------------------------------------------- |
| `subscription.created`           | The subscription exists                                                      |
| `subscription.payment_succeeded` | A period was paid for, including the first                                   |
| `subscription.payment_failed`    | Charging a period failed. The status is `past_due`, or the retries are spent |
| `subscription.canceled`          | The subscription ended, for any reason                                       |

An event carries the subscription as it was when the event happened. The two
payment events also carry the payment-interface identifier of the charge in
`payment`. Read the charge with `GetPayment` for the amount or the decline
reason. A `subscription.payment_failed` has no `payment` when the provider
refused to make the charge at all, for example because the saved method had
been removed.

A change of payment method and a cancellation scheduled for period end raise no
event. The caller made those changes and already knows about them.

## Receiving them

```ts
import {
  SubscriptionEvents,
  type SubscriptionEvent,
} from "@antelopejs/interface-subscriptions";

declare function alreadyHandled(eventId: string): Promise<boolean>;
declare function applyToAccount(event: SubscriptionEvent): Promise<void>;

SubscriptionEvents.register("billing", async (event) => {
  if (await alreadyHandled(event.id)) return;
  await applyToAccount(event);
});
```

`SubscriptionEvents` is a registering proxy, not a webhook route. You register
each handler under an identifier unique within your module. AntelopeJS
unregisters the handler when your module unloads.

Register handlers when your module starts. The implementation delivers an event
to the handlers registered at that time. An event raised while no handler is
registered reaches nobody, and the implementation does not keep it.

Delivery is **at least once**:

- A handler that throws or rejects has not handled the event. The implementation
  delivers the event again later, to every handler, so deduplicate on
  `event.id`.
- After a crash between a change and its delivery, the implementation delivers
  the event the next time it looks at that subscription.
- In a cluster, one instance delivers each event, to the handlers registered in
  that instance.

Events can arrive late. Do not treat an event as more recent than state you
already hold. `GetSubscription` always returns the current state.

## How implementations learn of them

Each implementation decides how it learns of events, and a consumer cannot see
the difference:

- The generic fallback raises them from its own renewal clock. It records each
  event in its database with the change that caused it.
- A native provider raises them from the provider's webhooks.

## Relation to payment events

Every subscription charge is an ordinary payment-interface payment, so its
`payment.*` events reach your payment webhook route as well. Their metadata
carries `SUBSCRIPTION_METADATA_KEY`, which is `antelopeSubscription`, set to the
identifier of the subscription:

```ts
import {
  VerifyWebhook,
  type WebhookRequest,
} from "@antelopejs/interface-payment";
import { SUBSCRIPTION_METADATA_KEY } from "@antelopejs/interface-subscriptions";

export async function handlePaymentWebhook(request: WebhookRequest) {
  const event = await VerifyWebhook(request);
  if (event?.payment?.metadata?.[SUBSCRIPTION_METADATA_KEY]) {
    return; // The subscription event handles this charge.
  }
}
```

Handle a subscription charge in one place. The subscription event says what the
charge meant, such as which period it paid for and whether the subscription is
now `past_due`.
