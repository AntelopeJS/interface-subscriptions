# Events

A subscription changes while nobody is calling, so a backend learns of renewals,
failures and endings from events.

## The event set

| Type                             | When                                                                         |
| -------------------------------- | ---------------------------------------------------------------------------- |
| `subscription.created`           | The subscription exists                                                      |
| `subscription.payment_succeeded` | A period was paid for, including the first                                   |
| `subscription.payment_failed`    | Charging a period failed; the status is `past_due`, or the retries are spent |
| `subscription.canceled`          | It ended, for any reason                                                     |

An event carries the subscription as it was when the event happened, and, for
the two payment events, the payment-interface identifier of the charge in
`payment`. Read the charge with `GetPayment` for the amount or the decline
reason.

Changing the payment method and scheduling a cancellation at period end raise no
event: the caller made those changes and already knows.

## Receiving them

```ts
import { SubscriptionEvents } from "@antelopejs/interface-subscriptions";

SubscriptionEvents.register("billing", async (event) => {
  if (await alreadyHandled(event.id)) return;
  await applyToAccount(event);
});
```

`SubscriptionEvents` is a registering proxy, not a webhook route. Handlers are
registered under an identifier unique within your module, and unregistered
automatically when your module unloads.

Delivery is **at least once**:

- A handler that throws or rejects has not handled the event, and it is delivered
  again later — to every handler, so de-duplicate on `event.id`.
- A crash between a change and its delivery means the event is delivered when the
  implementation next looks at that subscription.
- In a cluster, each event is delivered by one instance, to the handlers
  registered in that instance.

Events may arrive late, and should not be read as more recent than state you
already hold. `GetSubscription` is always current.

## How implementations learn of them

That is each implementation's business, and invisible to a consumer:

- the generic fallback raises them from its own renewal clock, recording each in
  its database with the change that caused it;
- a native provider raises them from the provider's webhooks.

## Relation to payment events

Every subscription charge is an ordinary payment-interface payment, so its
`payment.*` events reach your payment webhook route as well. They carry
`SUBSCRIPTION_METADATA_KEY` (`antelopeSubscription`) in their metadata, set to
the subscription's identifier:

```ts
const event = await VerifyWebhook(request);
if (event?.payment?.metadata?.[SUBSCRIPTION_METADATA_KEY]) {
  return; // a subscription charge: handled by the subscription event
}
```

Handle a subscription charge in one place. The subscription event is the one
that says what the charge meant — which period it paid for, whether the
subscription is now `past_due`.
