# Subscriptions

## Creating one

The payer is not present when a subscription charges, so the mandate is taken
first, through the payment interface. Create an on-session payment with
`savePaymentMethod: true`, `customer` and `returnUrl`, and persist its ID.
If it returns `requires_action`, send the payer to `redirectUrl`. Do not list
saved methods or start the subscription while the payment is still pending or
requires action, or if it failed or was canceled.

After a verified `payment.succeeded` or `payment.authorized` event, or a server
read with `GetPayment` reporting one of those states, use `ListPaymentMethods`
to find the saved method matching that payment's `paymentMethod`. Do not select
an unrelated method just because it appears first. The [README quick start](../README.md#quick-start)
shows the checkout and reconciliation steps separately.

`savePaymentMethod` cannot be combined with `offSession` — a mandate can only be
taken from a payer who is there. That first payment is an ordinary one-off; the
subscription starts after it, and its first period is a separate charge.

```ts
const subscription = await CreateSubscription(
  {
    reference: accountId,
    customer,
    paymentMethod: method.id,
    amount: { value: 1900, currency: "EUR" },
    interval: "month",
    intervalCount: 1,
  },
  `subscribe-${accountId}`,
);
```

Without a trial or a billing anchor, the first period is charged off-session
before `CreateSubscription` resolves:

| First charge             | Result                                                                                        |
| ------------------------ | --------------------------------------------------------------------------------------------- |
| Succeeded                | An `active` subscription                                                                      |
| Still settling (a debit) | An `active` subscription; if the charge later fails it goes `past_due`                        |
| Declined                 | Rejects with `SubscriptionPaymentError`, carrying the declined `Payment`. Nothing is created. |

Replaying the idempotency key within the provider-defined replay window returns
the saved outcome, including a rejection where retained by the provider.
After expiration, applications must reconcile uncertain payments and subscription
creation before retrying; the same key can create another charge.

## Periods

A period is `intervalCount` × `interval`, where the interval is `day`, `week`,
`month` or `year`. Every implementation accepts periods up to a year; a longer
one may be refused with `InvalidSubscriptionRequestError`.

Periods are counted from the billing anchor in calendar units, in UTC, and never
from the end of the previous period. A monthly subscription anchored on 31
January renews on 28 February (29 in a leap year), then on 31 March — not on the
28th of every month from then on.

`currentPeriodStart` and `currentPeriodEnd` describe the period most recently
billed for. The next charge is made at `currentPeriodEnd`.

## Trials and billing anchors

Both defer the first charge, and they are mutually exclusive.

- **`trialEnd`**: the subscription is `trialing` until then, nothing is charged,
  and the first paid period starts at the trial end.
- **`billingAnchor`**: the subscription is `active` until then — it exists and is
  in good standing — but nothing is charged until the anchor, where the first paid
  period starts.

In both cases the period before the first charge runs from creation to that
time, so `currentPeriodEnd` is the trial end or the anchor.

## Statuses

| Status     | Meaning                                                                                        |
| ---------- | ---------------------------------------------------------------------------------------------- |
| `trialing` | Before `trialEnd`. Nothing charged.                                                            |
| `active`   | The current period is paid for, or not yet due.                                                |
| `past_due` | Charging the current period failed. The implementation is retrying under its own policy.       |
| `canceled` | Ended. Terminal. `endedAt` and `endReason` (`requested` or `payment_failed`) say when and why. |

When a renewal fails, the period still advances: the new period is the current
one, and `past_due` says it is unpaid. When a retry succeeds the subscription is
`active` again in the same period; the cycle does not move.

### `past_due` is portable to report, not to predict

What happens after a failure is the implementation's: a native provider follows
the retry schedule configured in its dashboard, and the generic fallback follows
its documented policy (three retries, one, three and seven days apart, then the
subscription ends with `endReason: "payment_failed"`). Two subscriptions in the
same state may therefore behave differently on different providers. Decide access
from the status; do not schedule anything on the assumption of a retry date.

## Recovering a `past_due` subscription

If the saved method will not work again — an expired card — take a new mandate
on-session and switch to it:

```ts
await UpdateSubscriptionPaymentMethod(
  subscription.id,
  newMethodId,
  idempotencyKey,
);
```

Nothing is charged by the switch. The next scheduled attempt uses the new method.

## Cancelling

```ts
await CancelSubscription(id, `cancel-period-end-${id}`, "period_end"); // run out the paid period
await CancelSubscription(id, `cancel-now-${id}`, "now"); // end immediately
```

Use distinct keys for distinct operations. Reuse a key only when retrying the
same request; reusing the period-end key for immediate cancellation replays the
first outcome instead of applying the change.

- `period_end` sets `cancelAtPeriodEnd`. The status does not change until the
  period ends, at which point the subscription ends instead of renewing. Asking
  again is not an error.
- `now` ends it at once. Nothing is refunded; refunds are `RefundPayment` on the
  payment interface. A subscription set to end at period end can still be ended
  now.
- Either on a subscription that has already ended raises
  `InvalidSubscriptionStateError`, unless the idempotency key is a replay.

## Errors

| Error                             | When                                                                         |
| --------------------------------- | ---------------------------------------------------------------------------- |
| `SubscriptionNotFoundError`       | No subscription has that identifier under that `provider`                    |
| `InvalidSubscriptionRequestError` | A request outside the contract: a non-positive amount, a past trial end, ... |
| `InvalidSubscriptionStateError`   | A change to a subscription that has ended                                    |
| `SubscriptionPaymentError`        | The first period was charged and declined; nothing was created               |
| `SubscriptionError`               | The base class; also the call could not be made at all                       |

Each carries `providerCode` where the provider gave one.
`InvalidSubscriptionStateError.status` is an optional `SubscriptionStatus`
describing the actual state that blocked the operation. Its constructor is
`new InvalidSubscriptionStateError(message, status?, providerCode?)`.
