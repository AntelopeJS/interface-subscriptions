## Creating one

The payer is not present when a subscription charges, so you take the mandate
first, through the payment interface. Create an on-session payment with
`savePaymentMethod: true`, `customer`, and `returnUrl`, and persist its ID. If
it returns `requires_action`, send the payer to `redirectUrl`. Do not list saved
methods or start the subscription in these cases:

- The payment is still `pending` or `requires_action`.
- The payment is `failed` or `canceled`.

Wait for a verified `payment.succeeded` or `payment.authorized` event, or for a
server read with `GetPayment` that reports one of those states. Then use
`ListPaymentMethods` to find the saved method that matches the `paymentMethod`
of that payment. Do not select an unrelated method because it appears first. The
[README quick start](../README.md#quick-start) shows the checkout and the
reconciliation as separate steps.

`savePaymentMethod` cannot be combined with `offSession`, because only a payer
who is present can give a mandate. That first payment is an ordinary one-off
payment. The subscription starts after it, and its first period is a separate
charge.

```ts
import type { PaymentMethod } from "@antelopejs/interface-payment";
import { CreateSubscription } from "@antelopejs/interface-subscriptions";

export async function subscribe(
  accountId: string,
  customer: string,
  method: PaymentMethod,
) {
  return await CreateSubscription(
    {
      reference: accountId,
      customer,
      paymentMethod: method.id,
      amount: { value: 1900, currency: "EUR" },
      interval: "month",
      intervalCount: 1,
    },
    `subscribe-${accountId}`,
  );
}
```

Without a trial or a billing anchor, the implementation charges the first period
off-session before `CreateSubscription` resolves:

| First charge             | Result                                                                                        |
| ------------------------ | --------------------------------------------------------------------------------------------- |
| Succeeded                | An `active` subscription                                                                      |
| Still settling (a debit) | An `active` subscription. If the charge later fails, it goes `past_due`.                      |
| Declined                 | Rejects with `SubscriptionPaymentError`, carrying the declined `Payment`. Nothing is created. |

Within the replay window that the provider defines, a replayed idempotency key
returns the saved outcome. The outcome includes a rejection when the provider
retains it. After the window expires, reconcile uncertain payments and
subscription creation before you retry, because the same key can create another
charge.

## Periods

A period is `intervalCount` times `interval`. The interval is `day`, `week`,
`month`, or `year`. Every implementation accepts periods up to a year, which
`MAX_PORTABLE_PERIOD_DAYS` sets at 366 days. An implementation may refuse a
longer period with `InvalidSubscriptionRequestError`.

Implementations count periods from the billing anchor in calendar units, in UTC,
and never from the end of the previous period. A monthly subscription anchored
on 31 January renews on 28 February, or 29 February in a leap year. It then
renews on 31 March, not on the 28th of every month from then on.

`currentPeriodStart` and `currentPeriodEnd` describe the period most recently
billed for. The next charge happens at `currentPeriodEnd`.

## Trials and billing anchors

Both defer the first charge, and they are mutually exclusive.

- **`trialEnd`.** The subscription is `trialing` until then, and nothing is
  charged. The first paid period starts at the trial end.
- **`billingAnchor`.** The subscription is `active` until then. It exists and is
  in good standing, but nothing is charged until the anchor. The first paid
  period starts at the anchor.

In both cases, the period before the first charge runs from creation to that
time, so `currentPeriodEnd` is the trial end or the anchor.

## Statuses

| Status     | Meaning                                                                                        |
| ---------- | ---------------------------------------------------------------------------------------------- |
| `trialing` | Before `trialEnd`. Nothing charged.                                                            |
| `active`   | The current period is paid for, or not yet due.                                                |
| `past_due` | Charging the current period failed. The implementation is retrying under its own policy.       |
| `canceled` | Ended. Terminal. `endedAt` and `endReason` (`requested` or `payment_failed`) say when and why. |

When a renewal fails, the period still advances. The new period is the current
one, and `past_due` says that it is unpaid. When a retry succeeds, the
subscription is `active` again in the same period. The cycle does not move.

### `past_due` is portable to report, not to predict

The implementation decides what happens after a failure. A native provider
follows the retry schedule configured in its dashboard. The generic fallback
follows its documented policy. By default, it retries three times, one, three,
and seven days apart. When every retry has failed, the subscription ends with
`endReason: "payment_failed"`. Two subscriptions in the same state can therefore
behave differently on different providers. Decide access from the status. Do not
schedule anything on the assumption of a retry date.

## Recovering a `past_due` subscription

If the saved method will not work again, as with an expired card, take a new
mandate on-session and switch to it:

```ts
import {
  UpdateSubscriptionPaymentMethod,
  type Subscription,
} from "@antelopejs/interface-subscriptions";

export async function switchMethod(
  subscription: Subscription,
  newMethodId: string,
  idempotencyKey: string,
) {
  await UpdateSubscriptionPaymentMethod(
    subscription.id,
    newMethodId,
    idempotencyKey,
  );
}
```

The switch charges nothing. The next scheduled attempt uses the new method.

## Cancelling

```ts
import { CancelSubscription } from "@antelopejs/interface-subscriptions";

export async function cancel(id: string) {
  await CancelSubscription(id, `cancel-period-end-${id}`, "period_end"); // run out the paid period
  await CancelSubscription(id, `cancel-now-${id}`, "now"); // end immediately
}
```

Use distinct keys for distinct operations. Reuse a key only to retry the same
request. If you reuse the period-end key for immediate cancellation, the call
replays the first outcome and does not apply the change.

- `period_end` sets `cancelAtPeriodEnd`. The status does not change until the
  period ends. Then the subscription ends instead of renewing. Asking again is
  not an error.
- `now` ends the subscription at once. Nothing is refunded. A refund is a
  `RefundPayment` call on the payment interface. A subscription set to end at
  period end can still be ended now.
- Either timing on a subscription that has already ended raises
  `InvalidSubscriptionStateError`, unless the idempotency key is a replay.

## Errors

| Error                             | When                                                                              |
| --------------------------------- | --------------------------------------------------------------------------------- |
| `SubscriptionNotFoundError`       | No subscription has that identifier under that `provider`                         |
| `InvalidSubscriptionRequestError` | A request outside the contract, such as a non-positive amount or a past trial end |
| `InvalidSubscriptionStateError`   | A change to a subscription that has ended                                         |
| `SubscriptionPaymentError`        | The first period was charged and declined. Nothing was created.                   |
| `SubscriptionError`               | The base class. Also raised when the call could not be made at all.               |

Each error carries `providerCode` when the provider gave one.
`InvalidSubscriptionStateError.status` is an optional `SubscriptionStatus` that
describes the actual state that blocked the operation. Its constructor is
`new InvalidSubscriptionStateError(message, status?, providerCode?)`.
`SubscriptionNotFoundError` is also raised for an identifier that cannot be
parsed at all.
