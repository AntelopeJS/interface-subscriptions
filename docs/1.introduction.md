# Introduction

`@antelopejs/interface-subscriptions` defines provider-agnostic recurring
billing for AntelopeJS applications. A backend written against it bills a saved
payment method every period and learns what happened — paid, failed, ended —
without naming a provider, and without running a billing cycle of its own.

## Why a second interface

Every call in `@antelopejs/interface-payment` is request and response against
the provider. A subscription is different in kind: it is a long-lived object
that must be acted on **when nobody is calling**. It needs two things the
payment contract never needed:

1. **Durable state** — the subscription, its current period, its status.
2. **The passage of time** — something must fire at each renewal.

A provider with native subscriptions supplies both. A provider without them
leaves the merchant to fire each charge, and then something has to supply both
on the merchant's side. That something is a module with a database and a clock,
which is a subscriptions module's business and not a payment module's — so the
contract is its own interface, and:

- a payment module whose provider cannot do subscriptions does not implement it,
  rather than implementing it badly;
- the generic fallback, `@antelopejs/payment-subscriptions`, can depend on a
  database and a scheduler without forcing either on every payment consumer;
- consumers that do not bill recurrently do not carry the surface.

## Who fires the renewal

The question that sorts providers is not "is there a subscription object" but
"who fires each renewal charge". That is exactly what the fallback has to
supply.

| The provider fires renewals | The merchant fires them       |
| --------------------------- | ----------------------------- |
| Stripe, PayPal, Mollie      | Adyen, Checkout.com, Mangopay |

The split is even, so the fallback is half the providers rather than a rare edge.
[The capability matrix](./5.provider-capability-matrix.md) has the detail.

## The portable core

Expressible everywhere, including by the fallback:

- an amount, an interval and an interval count;
- a billing anchor (when the first paid period starts) or a trial end;
- a status, including `past_due`;
- cancelling now, or at the end of the period paid for;
- the current period's start and end.

Deliberately not modelled, because the fallback cannot honour them and a
contract only some implementations keep is a lie: proration, dunning schedules,
tax, coupons and discounts, metered billing, and more than one item per
subscription. A backend that needs one of these uses the provider's own
interface (`@antelopejs/interface-stripe`) alongside this one.

## Built on the payment interface

A subscription charges a method saved through `@antelopejs/interface-payment`,
off-session. That pair — one on-session payment that saves a method, then any
number of off-session charges against it — is the payment interface's portable
recurring primitive, and this interface adds nothing underneath it.

Identifiers cross the two interfaces unchanged: a subscription's `customer`,
`paymentMethod` and `latestPayment` are payment-interface identifiers from the
same account, and `provider` selects that account in both.

## Installation

```bash
pnpm add @antelopejs/interface-subscriptions
```

Wire a module that implements it alongside a payment module.

## Conventions

**Amounts are the payment interface's `Amount`**: integer minor units and an
uppercase ISO-4217 code.

**Times are Unix epoch milliseconds**, and periods are counted in UTC.

**Every mutating call takes an idempotency key**, positionally. Replaying it
returns the original outcome within the provider-defined replay window,
including rejections where the provider retains them. After expiration,
applications must reconcile uncertain payments before retrying; replay
protection is not indefinite.

**A failed renewal is a status, not an exception.** The subscription goes
`past_due` and a `subscription.payment_failed` event is raised. Only a declined
_first_ period rejects, because then there is no subscription to put in a state.

**`vendorData` is a read-only echo.** An implementation may surface what its
provider said; no request accepts provider-specific settings, because a
`Record<string, unknown>` that compiles against every provider and works on one
hides exactly the coupling this interface exists to prevent.
