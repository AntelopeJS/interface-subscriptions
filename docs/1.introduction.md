`@antelopejs/interface-subscriptions` defines recurring billing for AntelopeJS
applications that works with any payment provider. A backend written against it
bills a saved payment method every period. It learns whether each period was
paid, failed, or ended. It names no provider and runs no billing cycle of its
own.

## Why a second interface

Every call in `@antelopejs/interface-payment` is a request to the provider and
its response. A subscription is a different kind of thing. It is a long-lived
object that something must act on **when nobody is calling**. It needs two
things the payment contract never needed:

1. **Durable state.** The subscription, its current period, and its status.
2. **The passage of time.** Something must fire at each renewal.

A provider with native subscriptions supplies both. A provider without them
leaves the merchant to fire each charge, so something on the merchant's side has
to supply both. That something is a module with a database and a clock, which
belongs in a subscriptions module and not in a payment module. For that reason
the contract is its own interface, with these results:

- A payment module whose provider cannot do subscriptions does not implement the
  interface. It does not implement it badly either.
- The generic fallback, `@antelopejs/payment-subscriptions`, can depend on a
  database and a scheduler without forcing either on every payment consumer.
- Consumers that do not bill on a schedule do not carry the extra calls.

## Who fires the renewal

The question that sorts providers is "who fires each renewal charge". Whether
the provider has a subscription object does not decide it. The fallback has to
supply exactly that renewal charge.

| The provider fires renewals | The merchant fires them       |
| --------------------------- | ----------------------------- |
| Stripe, PayPal, Mollie      | Adyen, Checkout.com, Mangopay |

The split is even, so the fallback serves half the providers. It is not a rare
edge case. [The provider capability matrix](./5.provider-capability-matrix.md)
has the detail.

## The portable core

Every implementation can express these, the fallback included:

- An amount, an interval, and an interval count.
- A billing anchor, which is when the first paid period starts, or a trial end.
- A status, including `past_due`.
- Cancellation now, or at the end of the period paid for.
- The start and the end of the current period.

The contract leaves some features out on purpose. The fallback cannot honour
them, and a contract that only some implementations keep misleads its callers.
The features left out are proration, dunning schedules, tax, coupons and
discounts, metered billing, and more than one item per subscription. A backend
that needs one of these uses the provider's own interface, such as
`@antelopejs/interface-stripe`, alongside this one.

## Built on the payment interface

A subscription charges a method saved through `@antelopejs/interface-payment`,
off-session. The payment interface supports recurring charges portably with one
pair. One on-session payment saves a method, then any number of off-session
charges use it. This interface adds nothing underneath that pair.

Identifiers cross the two interfaces unchanged. The `customer`, `paymentMethod`,
and `latestPayment` of a subscription are payment-interface identifiers from the
same account. `provider` selects that account in both interfaces.

## Installation

```bash
pnpm add @antelopejs/interface-subscriptions
```

Wire a module that implements it alongside a payment module.

## Conventions

**Amounts are the `Amount` of the payment interface.** An amount is an integer
of minor units and an uppercase ISO-4217 code.

**Times are Unix epoch milliseconds.** Implementations count periods in UTC.

**Every mutating call takes an idempotency key.** It is a positional argument.
Within the replay window that the provider defines, a replayed key returns the
original outcome. The outcome includes a rejection when the provider retains
it. After the window expires, reconcile uncertain payments before you retry.
Replay protection does not last forever.

**A failed renewal is a status, not an exception.** The subscription goes
`past_due`, and the implementation raises a `subscription.payment_failed` event.
Only a declined _first_ period rejects, because then no subscription exists to
put in a state.

**`vendorData` is a read-only echo.** An implementation may expose what its
provider said. No request accepts settings for one provider. A
`Record<string, unknown>` that compiles against every provider but works on only
one would hide the coupling that this interface exists to prevent.
