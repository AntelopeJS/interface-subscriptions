# Implementing the interface

There are two kinds of implementation, and both are expected from the start.

## Native: the provider fires renewals

A payment module whose provider has first-class subscriptions (Stripe, PayPal,
Mollie) implements this interface beside `@antelopejs/interface-payment`, in the
same module, mapping each call onto the provider's subscription object. It owns
no clock and no database.

What it must do that the provider will not do for it:

- **Charge the first period at creation, or refuse.** A declined first charge
  rejects with `SubscriptionPaymentError` and leaves nothing behind. On Stripe
  this is `payment_behavior: "error_if_incomplete"`.
- **Count periods from the anchor**, in UTC calendar units. Providers that bill
  from an anchor already do.
- **Map the provider's statuses onto four.** Anything that means "a charge
  failed and the provider is retrying" is `past_due`; anything that has ended or
  will never charge again is `canceled`.
- **Raise the four events** from the provider's webhooks. A module that already
  normalises webhooks for the payment interface can raise subscription events from
  the same deliveries.
- **Mark charges** with `SUBSCRIPTION_METADATA_KEY` when it normalises the
  underlying payments, so a consumer can tell them from one-off payments.
- **Echo, never accept, `vendorData`.**

## Fallback: the merchant fires renewals

For every provider that leaves each charge to the merchant, wire
`@antelopejs/payment-subscriptions`. It implements this interface on top of any
payment-interface provider, keeps every subscription in
`@antelopejs/interface-database`, and fires renewals from its own clock — the
Redis scheduler when one is wired, polling the database when not.

A payment module should not implement this interface by embedding a clock of its
own: that would put a mandatory database and scheduler into a payment module.

## Wiring an implementation

The calls are declared directly as the public names, so the whole module is the
declaration:

```ts
import * as subscriptions from "@antelopejs/interface-subscriptions";
import { ImplementInterface } from "@antelopejs/interface-core";

export function construct(): void {
  ImplementInterface(subscriptions, {
    CreateSubscription,
    GetSubscription,
    ListSubscriptions,
    CancelSubscription,
    UpdateSubscriptionPaymentMethod,
    SubscriptionEvents: { register, unregister },
  });
}
```

`SubscriptionEvents` is a registering proxy: its implementation is a `register`
and `unregister` pair that keep the handlers your module delivers to.

List the interface in `antelopeJs.implements`, and the payment interface in
`dependencies`.

## The conformance suite

`dist/tests/*.test.js` ships in the package. `ajs module test` runs it
automatically against any module that lists this interface in
`antelopeJs.implements`.

It is weaker than the payment interface's suite, and the reason matters before
anyone reads a green run as a promise: **a test cannot wait a month.** Stripe has
test clocks, but Mollie and PayPal do not, so a portable suite cannot pin a
renewal, a trial ending, a failed retry or a period end. What it covers:

- creating a subscription that charges at once, a trial, a billing anchor;
- the first charge's shape and its metadata marker;
- idempotent replay of creation and cancellation;
- reading back, listing newest first and per customer;
- cancelling now and at period end, and refusing to change one that has ended;
- switching the payment method;
- unknown identifiers and every invalid request;
- a declined first period, when the provider can supply a method that saves and
  then declines;
- events, when they can reach the test process.

Everything time-driven is pinned instead by the generic fallback's own suite,
which drives an injected clock. That suite is the executable specification a
native implementation's renewal behaviour is checked against by eye.

| Variable                                            | Purpose                                                                     |
| --------------------------------------------------- | --------------------------------------------------------------------------- |
| `ANTELOPE_PAYMENT_TEST_METHOD`                      | A token that saves on-session and charges off-session.                      |
| `ANTELOPE_SUBSCRIPTIONS_TEST_METHOD_DECLINES_LATER` | A token that saves on-session and is declined off-session.                  |
| `ANTELOPE_SUBSCRIPTIONS_TEST_EVENTS`                | Set when the implementation's events reach the test process during the run. |
| `ANTELOPE_PAYMENT_TEST_CURRENCY`                    | ISO-4217 code to run against. Defaults to `EUR`.                            |

With nothing implementing the interface, the calls queue and the suite times
out; it cannot report green by accident.
