An implementation is one of two kinds, and the interface expects both from the
start.

## Native: the provider fires renewals

A payment module whose provider has first-class subscriptions, such as Stripe,
PayPal, or Mollie, implements this interface beside
`@antelopejs/interface-payment`, in the same module. It maps each call onto the
subscription object of the provider. It owns no clock and no database.

The module must do these things, which the provider does not do for it:

- **Validate with `ValidateSubscriptionRequest`** before anything reaches the
  provider, so every implementation enforces the portable request shape. If the
  provider checks its idempotency cache first, leave relative date validation
  to the provider. A replay must not fail because its original date has passed.
  An unknown customer or payment method is also an
  `InvalidSubscriptionRequestError`. It is never a `SubscriptionNotFoundError`,
  which is reserved for the subscription itself.
- **Report only its own subscriptions.** A provider account can hold
  subscriptions made elsewhere, such as in a hosted checkout or in the
  dashboard. They were not created through this interface and have no
  `reference`. Do not list them, read them, or raise events for them.
- **Charge the first period at creation, or refuse.** A declined first charge
  rejects with `SubscriptionPaymentError` and leaves nothing behind. On Stripe,
  this is `payment_behavior: "error_if_incomplete"`.
- **Count periods from the anchor**, in UTC calendar units. Providers that bill
  from an anchor already do.
- **Map the statuses of the provider onto four.** A status that means "a charge
  failed and the provider is retrying" is `past_due`. A status that has ended or
  will never charge again is `canceled`. Some providers can hold a subscription
  that will never charge again without ending it, such as Stripe's `unpaid`.
  Document that case, and tell the merchant to configure the provider to cancel
  instead.
- **Raise the four events** from the provider's webhooks. A module that already
  normalises webhooks for the payment interface can raise subscription events
  from the same deliveries.
- **Mark charges** with `SUBSCRIPTION_METADATA_KEY` when it normalises the
  underlying payments, so a consumer can tell them from one-off payments.
- **Echo, never accept, `vendorData`.** It is a `JsonObject`. Put strings,
  numbers, booleans, `null`, arrays, and plain objects in it, not a `Date`, a
  `Buffer`, or a function. The compiler rejects a value typed as an `interface`,
  such as a provider SDK object, and a `readonly` array. Build the object from a
  `type` alias or a literal, and spread a read-only array into a mutable one.
  `NaN` and `Infinity` compile, but `JSON.stringify` writes them as `null`.

## Fallback: the merchant fires renewals

For every provider that leaves each charge to the merchant, wire
`@antelopejs/payment-subscriptions`. It implements this interface on top of any
payment-interface provider and keeps every subscription in
`@antelopejs/interface-database`. It fires renewals from its own clock. That
clock is the Redis scheduler when one is wired. Otherwise it polls the
database.

Do not implement this interface in a payment module by embedding a clock in it.
That would make a database and a scheduler mandatory for the payment module.

## Wiring an implementation

Declare the calls under their public names, so the whole module is the
declaration. The `declare` lines below stand for your own implementations:

```ts
import * as subscriptions from "@antelopejs/interface-subscriptions";
import type { SubscriptionEventHandler } from "@antelopejs/interface-subscriptions";
import { ImplementInterface } from "@antelopejs/interface-core";

declare const CreateSubscription: typeof subscriptions.CreateSubscription;
declare const GetSubscription: typeof subscriptions.GetSubscription;
declare const ListSubscriptions: typeof subscriptions.ListSubscriptions;
declare const CancelSubscription: typeof subscriptions.CancelSubscription;
declare const UpdateSubscriptionPaymentMethod: typeof subscriptions.UpdateSubscriptionPaymentMethod;
declare function register(id: string, handler: SubscriptionEventHandler): void;
declare function unregister(id: string): void;

export function construct(): void {
  ImplementInterface(subscriptions, {
    CreateSubscription,
    GetSubscription,
    ListSubscriptions,
    CancelSubscription,
    UpdateSubscriptionPaymentMethod,
    SubscriptionEvents: { register, unregister },
  });
}
```

`SubscriptionEvents` is a registering proxy. Its implementation is a `register`
and `unregister` pair that keep the handlers your module delivers to.

List the interface in `antelopeJs.implements`, and list the payment interface in
`dependencies`.

## `ValidateSubscriptionRequest`

`ValidateSubscriptionRequest(request: SubscriptionRequest, now?: number): void`
checks the portable request rules synchronously. Supply `now` to also check
that trial and billing dates are in the future. `now` is in Unix epoch
**milliseconds**, such as `Date.now()`, not seconds. Pass your injected clock in
tests or in an implementation that controls time.

```ts docs-check
import {
  ValidateSubscriptionRequest,
  type SubscriptionRequest,
} from "@antelopejs/interface-subscriptions";

export function validateBeforeCreation(request: SubscriptionRequest): void {
  ValidateSubscriptionRequest(request, Date.now());
}
```

The function returns `undefined` on success. Otherwise it throws
`InvalidSubscriptionRequestError` with a message that names the first failed
rule:

- `reference`, `customer`, and `paymentMethod` must be non-empty.
- `amount.value` must be a positive integer of minor units. `amount.currency`
  must contain exactly three uppercase letters. The helper checks the format,
  not membership in an ISO currency registry.
- `interval` must be `day`, `week`, `month`, or `year`. An explicit
  `intervalCount` must be a positive integer.
- `trialEnd` and `billingAnchor` are mutually exclusive. Each one, if supplied,
  must be finite. When `now` is supplied, each one must also be strictly
  greater than `now`. Equality is invalid.

Omit `now` only when your provider validates future dates after it resolves
idempotent replays. Stripe uses this form. A retry with the original key and
parameters can return the saved subscription after its trial or billing anchor
has passed. A new request with a past date still fails at the provider. If your
implementation owns its idempotency storage, resolve replays before you apply
relative date validation yourself.

The helper does not contact a provider. It does not check that the customer or
the saved method exists, and it does not enforce the maximum periods of a
provider. Make those checks separately, and report invalid requests with
`InvalidSubscriptionRequestError` too.

## The conformance suite

`dist/tests/*.test.js` ships in the package. `ajs module test` runs the suite
against any module that lists this interface in `antelopeJs.implements`.

The suite checks less than the suite of the payment interface. Know why before
you read a green run as a promise: **a test cannot wait a month.** Stripe has
test clocks, but Mollie and PayPal do not. A portable suite therefore cannot pin
a renewal, a trial end, a failed retry, or a period end. The suite covers these
cases:

- Creating a subscription that charges at once, one with a trial, and one with a
  billing anchor.
- The shape of the first charge and its metadata marker.
- Idempotent replay of creation and cancellation.
- Reading back, and listing newest first and per customer. The test reads the
  precision of your clock from the trailing zeros of `createdAt`, and waits a
  little over one tick of it between two creations. Report `createdAt` at the
  precision you list by.
- Cancelling now and at period end, and refusing to change a subscription that
  has ended.
- Switching the payment method.
- Unknown identifiers and every invalid request.
- A declined first period, when the provider can supply a method that saves and
  then declines.
- Events, when they can reach the test process.

The generic fallback has its own suite, which drives an injected clock and pins
everything that depends on time. That suite is the executable specification. Check the
renewal behaviour of a native implementation against it by eye.

| Variable                                            | Purpose                                                                     |
| --------------------------------------------------- | --------------------------------------------------------------------------- |
| `ANTELOPE_PAYMENT_TEST_METHOD`                      | A token that saves on-session and charges off-session.                      |
| `ANTELOPE_SUBSCRIPTIONS_TEST_METHOD_DECLINES_LATER` | A token that saves on-session and is declined off-session.                  |
| `ANTELOPE_SUBSCRIPTIONS_TEST_EVENTS`                | Set when the implementation's events reach the test process during the run. |
| `ANTELOPE_PAYMENT_TEST_CURRENCY`                    | ISO-4217 code to run against. Defaults to `EUR`.                            |

When nothing implements the interface, the calls queue and the suite times
out. It cannot report green by accident.
